# Accessibility audit (wave 3a)

Scope: semantics, keyboard navigation and screen-reader support across pages and shared components.
No visual design changes were made; the only styling touched is focus-visible rings and sr-only text.

## Verified by the new spec

`app/e2e/a11y.spec.ts` (8 tests):

- Login: Tab reaches email, password, submit in order.
- Register: submit with empty fields links each error through `aria-describedby` and `role="alert"`, including the consent checkbox.
- Log workout modal: opened with Enter from the trigger, has dialog semantics, Escape closes it and focus returns to the trigger.
- Guided run: started with the keyboard, distance progressbar exposes `role="progressbar"` with `aria-valuenow` and `aria-valuemax`.
- Today: first Tab focuses the skip link, Enter moves focus to `main`, race and week progressbars are exposed by name.
- Settings profile: username input has the accessible label "Korisničko ime".
- Friends: add-friend input has the accessible label "Ime profila".
- Leaderboard: rows are list items and expose readable text.

## Known limitations

- No axe-core or automated rule engine is used because new dependencies are out of scope; the spec asserts targeted semantics instead.
- Headless Chromium cannot confirm actual screen-reader speech, only the exposed accessibility tree.
- SegmentedControl uses `aria-pressed` buttons in a group rather than a radio group; it is keyboard operable with arrow keys but is not a native radio pattern.
- The modal focus trap relies on window keydown events; focus moved outside the browser window cannot be intercepted.
- Avatar images keep the generic "Avatar" alt because the visible name sits next to them; making the alt the name would duplicate announcements.
- Animated counters (CountUp) update text content; a screen reader may in rare cases announce an intermediate value.
